SECTION 2 — WEEKLY SET TARGET EDGE CASES
Source: ProgramGenerator.resolveWeeklySetTarget()
═══════════════════════════════════════════════════════════════════════

Function signature:
  resolveWeeklySetTarget(muscle, week, blockType, muscleTier, experience,
                          calorieContext, calibration, nextWeekAdjustment,
                          previousBlockPeakSets)

Pipeline:
  1. If deload → return mv(muscle) immediately
  2. Compute baseMEV (calibration-blended or experience-scaled)
  3. Add priorityBonus (+4 if priority tier)
  4. Apply blockMultiplier
  5. Apply weekAdjustment (skip on week 1)
  6. Apply previousBlockPeakSets cap (week 1 only: min(result, peak - 2))
  7. Clamp to MRV ceiling (G1)
  8. Floor at MV (G2)

───────────────────────────────────────────────────────────────────────
2.1  Deload week for every experience level
───────────────────────────────────────────────────────────────────────
When blockType == .deload, resolveWeeklySetTarget returns mv(muscle)
immediately, bypassing ALL other logic.

mv() values:
  Chest=6, Back=6, Quads=6, Calves=6
  Hamstrings=4, Glutes=4, Delts=4, Triceps=4, Biceps=4

These values are FIXED regardless of experience level. A beginner and
an elite lifter get the same deload volume. This is by design — deloads
are meant to be minimal.

Edge cases:
  • Experience level does NOT affect deload volume → PASS
  • Muscle tier does NOT affect deload volume → PASS
  • Calorie context does NOT affect deload volume → PASS
  • Priority muscles still get only mv() during deload → PASS

VERDICT: PASS

───────────────────────────────────────────────────────────────────────
2.2  Week 1 with previousBlockPeakSets at various values
───────────────────────────────────────────────────────────────────────
Logic: if week == 1 && previousBlockPeakSets exists:
       result = min(result, peak - 2)

Example: Chest, intermediate, neutral tier, accumulation block
  baseMEV = scaledMEV("Chest", .intermediate) = Int(6 * 1.4) = 8
  priorityBonus = 0
  blockMultiplier = 1.0 (accumulation)
  base = Int(8 * 1.0) = 8
  weekAdjustment = 0 (week 1 always 0)
  result = 8

  previousBlockPeakSets = 14 → min(8, 14-2=12) = 8 (no change — base < peak-2)
  previousBlockPeakSets = 10 → min(8, 10-2=8) = 8 (equal — no change)
  previousBlockPeakSets = 8  → min(8, 8-2=6) = 6 (CAPPED — reduced by 2)
  previousBlockPeakSets = 4  → min(8, 4-2=2) = 2 (CAPPED — heavy reduction)
  previousBlockPeakSets = 2  → min(8, 2-2=0) = 0 (result = 0, then G2 raises to mv)
  previousBlockPeakSets = 0  → min(8, 0-2=-2) = -2 (negative! Then G2 raises to mv)

Edge cases:
  • peak - 2 can go negative → G2 (floorAtMV) catches this. PASS.
  • peak = nil → cap doesn't apply, result stays at computed base. PASS.
  • Week 2+ → previousBlockPeakSets is ignored entirely. PASS.

VERDICT: PASS

───────────────────────────────────────────────────────────────────────
2.3  nextWeekAdjustment at extreme values
───────────────────────────────────────────────────────────────────────
weekAdjustment = (week == 1) ? 0 : nextWeekAdjustment

Extreme positive: nextWeekAdjustment = +10
  base = 8 (intermediate, chest, accumulation)
  result = 8 + 10 = 18
  mrv = effectiveMRV("Chest", .intermediate, .neutral, .unknown)
       = scaledMRV("Chest", .intermediate) * 1.0 * 1.0
       = Int(22 * 1.2) * 1 * 1 = 26
  Clamped: min(18, 26) = 18
  Floored: max(18, 6) = 18
  Result: 18. Not capped because MRV is high enough.

Extreme negative: nextWeekAdjustment = -10
  result = 8 + (-10) = -2
  Clamped: min(-2, 26) = -2
  Floored: max(-2, 6) = 6
  Result: 6 (raised to MV floor). G2 catches negative results.

Zero adjustment: nextWeekAdjustment = 0
  result = 8 + 0 = 8. No change.

Week 1 with any adjustment:
  weekAdjustment forced to 0 → adjustment ignored. PASS.

Edge cases:
  • Extreme positive → G1 clamps to MRV. PASS.
  • Extreme negative → G2 floors at MV. PASS.
  • +10 with priority tier muscle:
    baseMEV = 8, priorityBonus = 4, base = 12
    result = 12 + 10 = 22
    mrv = Int(22 * 1.2) * 1.5 * 1.0 = 39
    Result: 22 (under MRV, unclamped). PASS.

VERDICT: PASS

───────────────────────────────────────────────────────────────────────
2.4  Every calorie context × experience level combination
───────────────────────────────────────────────────────────────────────
CalorieContext.mrvModifier values:
  .unknown / .surplus / .maintenance → 1.0
  .mildDeficit → 0.90
  .moderateDeficit → 0.85
  .aggressiveDeficit → 0.75

effectiveMRV = scaledMRV * tier.multiplier * calorieContext.mrvModifier

Sample: Chest, neutral tier
  Experience     scaledMRV   surplus   maintenance   mildDef   modDef   aggDef
  beginner       22          22        22            19        18       16
  intermediate   26          26        26            23        22       19
  advanced       29          29        29            26        24       21
  elite          31          31        31            27        26       23

NOTE: CalorieContext only affects the MRV CEILING. It does NOT affect
baseMEV or the starting set target. So calorie context only matters
when the computed target exceeds the adjusted MRV.

  baseMEV = Int(6 * 2.3) = 13
  priorityBonus = 4
  base = 17 (accumulation multiplier 1.0)

  Result: 17 (under MRV cap). Deficit doesn't constrain here.

  base = 17 + 6 = 23
  mrv = 34
  Result: 23 (still under cap). Even aggressive deficit allows high volume
  for elite priority muscles.

  Chest, intermediate, maintenance, moderate deficit:
  baseMEV = Int(6 * 1.4) = 8
  priorityBonus = 0

Effect on volume:

  • MRV ceiling reduced: effectiveMRV = scaledMRV * 0.7 * calorieModifier
  • baseMEV is NOT reduced by tier (tier only affects MRV and effectiveMEV)

  Result: 8 (within bounds)

  baseMEV = Int(6 * 2.3) = 13

2.7  Calibration confidence at 0%, 50%, 100%
───────────────────────────────────────────────────────────────────────
Calibration blending formula:
  confidence = min(1.0, weeksTracked / 12.0)
  baseMEV = Int(scaledMEV * (1 - confidence) + adjustedMEV * confidence)

Only activates when calibration exists AND confidence != .seeded.

0% (weeksTracked = 0, confidence = .seeded):
  → Calibration bypassed entirely (if let cal = calibration,
    cal.confidence != .seeded guard fails)
  → baseMEV = scaledMEV(experience-based). PASS.

50% (weeksTracked = 6, confidence = 6/12 = 0.5):
  scaledMEV = 8, adjustedMEV = 12 (calibration discovered higher MEV)
  baseMEV = Int(8 * 0.5 + 12 * 0.5) = Int(10) = 10. PASS.

100% (weeksTracked = 12+, confidence = 1.0):
  baseMEV = Int(8 * 0 + 12 * 1.0) = 12.
  Fully trusts calibration. PASS.

Edge case: weeksTracked = 24 → confidence = min(1.0, 24/12) = 1.0.
  Same as 100%. PASS.

Edge case: adjustedMEV = 0 (calibration somehow zeroed):
  At 100%: baseMEV = 0. Then base = 0 + priorityBonus.
  Result clamped by G2 to MV. PASS (safety net works).

Edge case: calibration exists but confidence == .seeded:
  Guard fails → uses experience-scaled MEV. PASS.

SECTION 4 — VOLUME DECISION ENGINE EDGE CASES
Source: VolumeDecisionEngine.decide() + evaluateStimulus()
═══════════════════════════════════════════════════════════════════════

Decision tree priority order:
  1. ifiZone == .acuteOverreach → deload (HIGHEST PRIORITY)
  2. stallDiagnosis == .fatigueStall → deload
  3. progressionRule == .progress OR e1rmTrend > noiseFloor → holdVolume
  4. respondsBetterTo == .lowVolumeHighIntensity → holdVolume
  5. progressionRule == .backoff → holdVolume
  6. stallDiagnosis == .intensityStall → holdVolume
  7. ifiZone == .fatigued OR stallDiagnosis == .volumeStall → reduceSets
  8. evaluateStimulus() → addSets (if stimulus insufficient + confidence ≥ 0.5)
  9. Default → holdVolume

Key: Later checks only fire if ALL earlier checks fail.

───────────────────────────────────────────────────────────────────────
4.1  Complete combination matrix
───────────────────────────────────────────────────────────────────────

FORMAT: [progressionRule | ifiZone | stallDiagnosis | e1rmTrend |
         respondsBetterTo | blockPhase] → DECISION

DELOAD CASES (unconditional):

[any | .acuteOverreach | any | any | any | any] → deload
  Reason: IFI ≥ 0.40 indicates severe fatigue accumulation.

[any | any | .fatigueStall | any | any | any] → deload
  Reason: IFI trend >0.25 + declining e1RM = systemic fatigue.

  EXCEPTION: What if progressionRule == .progress AND stallDiagnosis == .fatigueStall?
  Check order: acuteOverreach (step 1) → fatigueStall (step 2) → progress (step 3)
  → fatigueStall wins. DELOAD even if user is progressing.
  This could be wrong: if e1RM is rising (.progress) but IFI is high,
  the user may still be adapting. The fatigueStall diagnosis could be
  stale (from consecutiveStallDiagnoses >= 1 cache).
  FLAGGED: Potential false deload when progress + fatigueStall coexist.

HOLD CASES:

[.progress | fresh/optimal | noStall/truePlateau/volumeStall/intensityStall |
 any | any | any] → holdVolume
  Reason: Load is progressing; volume is not the lever.

[.hold | fresh/optimal | noStall | >noiseFloor | any | any] → holdVolume
  Reason: e1rmTrend positive beyond noise → progressing via e1RM.

[any | fresh/optimal | noStall | within noise | .lowVolumeHighIntensity |
 any] → holdVolume
  Reason: N=1 classification says user responds to intensity, not volume.

[.backoff | fresh/optimal | noStall | any | any | any] → holdVolume
  Reason: Weight was just reduced; give it time.

[any | fresh/optimal | .intensityStall | any | any | any] → holdVolume
  Reason: Low fatigue + flat strength = user isn't pushing hard enough.
  Adding volume won't help; intensity is the lever.

REDUCE CASES:

[.hold | .fatigued | noStall/truePlateau | ≤noiseFloor |
 not lowVolumeHighIntensity | any] → reduceSets(min(2, current-mev))
  Reason: Fatigued IFI zone indicates too much accumulated fatigue.

[.hold | fresh/optimal | .volumeStall | ≤noiseFloor |
 not lowVolumeHighIntensity | any] → reduceSets(min(2, current-mev))
  Reason: Volume stall = IFI trend > 0.30, too much volume.

  Edge case: currentSets == mev
    setsToRemove = min(2, 0) = 0 → holdVolume (can't reduce below MEV)

  Edge case: currentSets == mev + 1
    setsToRemove = min(2, 1) = 1 → reduceSets(1)

ADD CASES:

[.hold | .fresh | noStall/truePlateau | within noise |
 not lowVolumeHighIntensity | .earlyAccumulation] → evaluateStimulus

  evaluateStimulus scoring:
    Signal 1 (35%): weeksAtCurrentLoad >= requiredWeeks for blockPhase
      .postDeloadReintro: requiredWeeks=999 → never fires
      .earlyAccumulation: requiredWeeks=3
      .lateAccumulation:  requiredWeeks=2
      .intensification:   requiredWeeks=1 (DEAD CODE — blockPhase never
                          returns .intensification; see Section 9)
      .deload:            requiredWeeks=999 → never fires

    Signal 2 (30%): e1rmTrend evaluation
      declining → 0 (not a stimulus issue)
      flat → 0.30 (full weight)
      rising → 0 (still improving)

    Signal 3 (25%): IFI zone
      .fresh → 0.25 (full weight — capacity available)
      .optimal → 0.10 (partial weight)
      .fatigued/.acuteOverreach → never reaches here (caught earlier)

    Signal 4 (10%): Block phase
      .lateAccumulation + flat e1RM → 0.10

    Threshold: stimScore > 0.5 AND confidence >= 0.5

    Maximum possible score:
      0.35 (signal 1) + 0.30 (signal 2) + 0.25 (signal 3) + 0.10 (signal 4) = 1.0

    Minimum to trigger addSets: stimScore > 0.5
      Requires at minimum: signal 2 (0.30) + signal 3 (0.25) = 0.55
      OR: signal 1 (0.35) + signal 2 (0.30) = 0.65
      OR: signal 1 (0.35) + signal 3 (0.25) = 0.60

    So addSets requires EITHER:
      a) flat e1RM + fresh IFI (0.55 > 0.5) ✓
      b) stalled weeks + flat e1RM (0.65 > 0.5) ✓
      c) stalled weeks + fresh IFI (0.60 > 0.5) ✓
    But NOT:
      d) flat e1RM alone (0.30 ≤ 0.5) ✗
      e) fresh IFI alone (0.25 ≤ 0.5) ✗
      f) stalled weeks alone (0.35 ≤ 0.5) ✗

    Confidence threshold:
      When signal 1 fires: confidence includes dur (0.x)
      When signal 2 fires (flat): confidence includes 0.85
      When signal 3 fires (fresh): confidence includes 0.85
      Average of these values easily exceeds 0.5 threshold.

  Sets added when fresh: 2 (capped by mrv - currentSets)
  Sets added when optimal: 1 (capped by mrv - currentSets)

  Edge case: currentSets == mrv
    capped = min(setsToAdd, 0) = 0 → holdVolume

  Edge case: currentSets == mrv - 1
    capped = min(2, 1) = 1 for fresh; min(1, 1) = 1 for optimal

───────────────────────────────────────────────────────────────────────
4.2  respondsBetterTo effects
───────────────────────────────────────────────────────────────────────

.lowVolumeHighIntensity:
  → holdVolume (step 4 in decide). Never adds sets regardless of other signals.
  This is a STRONG override: even if IFI is fresh, e1RM is flat, and
  weeks have stalled, volume won't increase.

.highVolumeLowIntensity:
  → No special handling in decide(). Falls through to normal logic.
  If evaluateStimulus triggers, sets are added normally.
  No volume BONUS for this classification — it just allows normal flow.

.balanced / nil:
  → Same as .highVolumeLowIntensity (no special handling).

OBSERVATION: .highVolumeLowIntensity and .balanced produce identical
behavior. The classification only matters for .lowVolumeHighIntensity.

VERDICT: PASS (but .highVolumeLowIntensity has no unique behavior)

───────────────────────────────────────────────────────────────────────
4.3  blockPhase effects on evaluateStimulus
───────────────────────────────────────────────────────────────────────

.postDeloadReintro:
  requiredWeeks = 999 → signal 1 never fires.
  Only signals 2+3 can trigger addSets.
  Minimum: 0.30 + 0.25 = 0.55 > 0.5 ✓
  So addSets CAN fire during postDeloadReintro, but only if e1RM is
  flat AND IFI is fresh. This is cautious — correct behavior after deload.

.earlyAccumulation:
  requiredWeeks = 3. Signal 1 fires after 3+ weeks stalled.
  Normal behavior.

.lateAccumulation:
  requiredWeeks = 2. Signal 1 fires after 2+ weeks stalled (more sensitive).
  Signal 4 also fires if e1RM flat → extra 0.10.
  More aggressive about adding volume late in accumulation. Correct.

.intensification:
  requiredWeeks = 1. Signal 1 fires after 1 week.
  DEAD CODE: blockPhase computed property NEVER returns .intensification.
  See Section 9. During intensification blocks, blockPhase returns
  .earlyAccumulation or .lateAccumulation, so requiredWeeks = 3 or 2.

.deload:
  requiredWeeks = 999 → signal 1 never fires.
  But deload is caught by the deload early-return in resolveWeeklySetTarget,
  so evaluateStimulus is never called during deload in practice.

───────────────────────────────────────────────────────────────────────
4.4  Ambiguous or potentially wrong combinations
───────────────────────────────────────────────────────────────────────

AMBIGUOUS: [.progress | .fatigued | .noStall | >noiseFloor | any | any]
  Step 1: not acuteOverreach → continue
  Step 2: not fatigueStall → continue
  Step 3: progressionRule == .progress → holdVolume
  But IFI is .fatigued! User is progressing weight but accumulating
  fatigue. HoldVolume may allow fatigue to build to dangerous levels.
  FLAGGED: Consider whether fatigue+progress should trigger a monitor
  signal or proactive volume reduction.

AMBIGUOUS: [.hold | .optimal | .truePlateau | within noise | .balanced |
            .earlyAccumulation] with weeksAtCurrentLoad = 1
  Steps 1-7 pass. evaluateStimulus: signal 1 fails (1 < 3 weeks).
  Signals 2+3: 0.30 + 0.10 = 0.40 < 0.5 → holdVolume.
  User is plateaued but system waits. Could be frustrating for the user
  but correct — need more data before adding volume.

POTENTIALLY WRONG: [.hold | .fresh | .volumeStall | ≤noiseFloor | any | any]
  Step 7: ifiZone == .fatigued? No (fresh). stallDiagnosis == .volumeStall? Yes!
  → reduceSets.
  But user's IFI is FRESH, contradicting the volume stall diagnosis.
  The volumeStall diagnosis (IFI trend > 0.30) may be stale from a
  previous session while current IFI is fresh. The engine trusts the
  diagnosis over the current IFI zone.
  FLAGGED: Stale volumeStall + fresh IFI → possibly wrong reduceSets.

VERDICT for Section 4: PASS with flagged ambiguities above

  Chest: result = min(base, 12-2=10). If base > 10, capped to 10.
  This ensures new block starts below previous peak — progressive overload
  across blocks via volume ramp.

Effects on exercise selection:
  T1 continuity bonus: blockNumber(1) > 1 is false! Wait — blockNumber
  is the parameter passed to selectExercisesForMuscle. In generateBlock(),
  it's the blockNumber parameter of generateBlock() itself.

  In finalizeWorkout(): called with blockNumber: inst.totalBlocksCompleted.
  After first block transition: totalBlocksCompleted = 1.
  So blockNumber = 1, and 1 > 1 is false → continuity bonus doesn't fire.

  Wait, but blockNumber is compared to 1: `blockNumber > 1`. So:
    blockNumber 0 → false (first block)
    blockNumber 1 → false (second block!)
    blockNumber 2 → true (third block)

  FINDING: Continuity bonus only fires from block 3 onward (blockNumber ≥ 2).
  Block 2 (blockNumber=1) treats all exercises as equally fresh.
  This means the T1 anchor could CHANGE between block 1 and block 2,
  even though the user established a progression on block 1's exercise.

  POTENTIAL GAP: Off-by-one in continuity bonus. Should be blockNumber >= 1
  (or > 0) to enable continuity from the second block onward.

  T2 rotation: previousBlockExerciseKeys is populated. Exercises used in
  block 1 are "resting", unused ones are "rested". T2 selection prefers

8.6  Session duration budget: sessionDurationTarget = 45 minutes (short)
───────────────────────────────────────────────────────────────────────
Duration filter in generateBlock():
  estimatedMinutes = (sessionTotalSets + slot.sets) * (45 + slot.restSeconds) / 60
  if estimatedMinutes > sessionDurationTarget + 20 → skip T3, skip T2 if >16 sets

  Each T1 slot: (sets * (45+210)) / 60 ≈ sets * 4.25 min
  5 T1 sets for Chest ≈ 21 minutes
  After 15 total sets: 15 * ~3.25 ≈ 49 minutes (still under 65)
  After 16 total sets: ~52 minutes (under 65)
  After 20 total sets: ~65 minutes (at threshold)

  T3 exercises start being skipped around 18-20 total sets.
  T2 exercises skipped above 16 sets if over duration.

  For a 4-day upper session with 5 muscles:
  After Chest T1(5) + Back T1(5) + Delts T1(3) = 13 sets, ~42 min.
  Add Triceps T2(2): 15 sets, ~49 min.
  Add Biceps T2(2): 17 sets, ~55 min.
  T3 for any muscle: ~60 min. If T3 rest is 90s:
    (17+3) * (45+90)/60 = 20 * 2.25 = 45. But this isn't cumulative...

  Actually the formula is: (sessionTotalSets + slot.sets) * (45 + slot.restSeconds) / 60
  This is NOT a running total — it recalculates for the entire session
  each time, using the CURRENT slot's restSeconds for ALL sets.

  This is a ROUGH estimate, not exact. If slot.restSeconds = 90 (T3):
  (17 + 3) * (45 + 90) / 60 = 20 * 135 / 60 = 45 min → under 65.

  If slot.restSeconds = 210 (T1):
  (17 + 5) * (45 + 210) / 60 = 22 * 255 / 60 = 93.5 → over 65!

  OBSERVATION: The duration estimate uses the CURRENT SLOT's rest seconds
  to estimate the entire session. T1 slots with 210s rest will heavily
  overestimate, T3 slots with 90s rest will underestimate. This makes
  the budget filter inconsistent — T1 slots are more likely to be
  filtered (even though they should never be filtered per the code:
  T3 filtered first, T2 only above 16 sets). Since T1 is always added
  first and the check skips it for T3/T2 tiers, this inconsistency
  only manifests for LATER T1 slots of subsequent muscles in the same

  Actually re-reading: the filter is:
    if slot.exerciseTier == .tier3 { continue }
    if slot.exerciseTier == .tier2 && sessionTotalSets > 16 { continue }
  So T1 slots are NEVER filtered by duration. Only T3 (always filtered
  when over budget) and T2 (filtered when >16 total sets AND over budget).

  For 45-minute target: T3 exercises will be aggressively trimmed, T2
  exercises may also be trimmed if sessions have many muscles. T1 anchors
  always preserved. CORRECT behavior.

───────────────────────────────────────────────────────────────────────
9.1  G3 (deloadSetFloor) and G4 (clampRPE) defined but not wired
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

G3: deloadSetFloor is never called. Deload sets are controlled by
mv(muscle) which always returns ≥ 4. G3's floor of 2 is redundant
unless mv() changes. No risk currently, but the guard rail provides
no actual protection.

G4: clampRPE is never called. Generated RPE maxes at 9.0 (peak × T1),
below the 9.5 threshold. User-logged RPE is handled by applyRPEBrake()
which has its own 9.5 check. G4 is redundant.

Recommendation: Either wire these guards or remove them to reduce
dead code. If wired, G3 should wrap resolveWeeklySetTarget's deload
return, and G4 should wrap the RPE assignment in generateBlock.

───────────────────────────────────────────────────────────────────────
9.2  ProgressionRate .fast modifier implementation
───────────────────────────────────────────────────────────────────────
Code (RPEEngine.swift lines 177-181):
  case .fast:
      if exerciseTier == .tier1 && rule == .progress {
          baseWeight += increment * 0.5
      }

Analysis: baseWeight is ALREADY set to lastWorkingWeight + increment
(from the .progress case at line 137). Then .fast adds another
increment * 0.5. So the total progression is:

  baseWeight = lastWorkingWeight + increment + (increment * 0.5)
             = lastWorkingWeight + increment * 1.5

This means .fast users progress 50% faster on T1 exercises when the
progression rule is .progress. This is additive to the base increment,
not a multiplier on the existing weight.

Example (imperial, T1, weight = 200lb):
  increment = 10.0 (≥185lb threshold)
  Normal progression: 200 + 10 = 210
  Fast progression:   200 + 10 + 5 = 215

Example (metric, T1, weight = 80kg):
  increment = 2.5
  Normal: 80 + 2.5 = 82.5
  Fast:   80 + 2.5 + 1.25 = 83.75 → rounded to 82.5 or 85.0

CONCERN: The 50% bonus increment is added BEFORE plate rounding.
After rounding (metric 2.5kg plates), 83.75 rounds to either 82.5
or 85.0 depending on rounding rules. RPETable.roundToPlate uses
standard .rounded(), so 83.75 / 2.5 = 33.5 → rounds to 34 → 85.0.
This effectively doubles the increment (2.5 + 2.5 = 5.0 effective)!

For imperial: 215 / 5 = 43 → 215. Exact, no rounding issue. The
effective increment is 15lb vs normal 10lb.

The implementation IS correct per its intent: .fast lifters get bigger
jumps. Whether 50% is the right amount depends on training philosophy.
The code is consistent with the task description's specification:
"progressionRate .fast adds 50% to tier1 increment."

VERDICT: Confirmed correct. The 50% bonus on increment (not weight)
is the intended behavior. Plate rounding may amplify the effect for
metric users, which is a minor imprecision but not a bug.

───────────────────────────────────────────────────────────────────────
9.3  BlockPhase .intensification is never returned by computed property
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

The blockPhase computed property on UserProgramInstance (Models.swift
line 793-798) returns:
  .deload            (if blockType == .deload)
  .postDeloadReintro (if blockWeek == 1 && totalBlocksCompleted > 0)
  .earlyAccumulation (if blockWeek ≤ midpoint)
  .lateAccumulation  (if blockWeek > midpoint)

It NEVER returns .intensification, even when blockType == .intensification.

Impact:
  a) RPEEngine.recommend() line 134: blockPhase == .intensification →
     increment *= 1.3. This NEVER fires. Intensification blocks do NOT
     get 30% larger weight increments. DEAD CODE.

  b) VolumeDecisionEngine.evaluateStimulus() signal 1:
     .intensification requiredWeeks = 1. NEVER reached.
     During intensification blocks, requiredWeeks = 3 or 2
     (earlyAccumulation or lateAccumulation), which is more conservative
     than the intended 1-week sensitivity.

  c) blockPhase == .intensification is never the value passed to any
     downstream consumer.

Root cause: blockPhase is computed from blockType + blockWeek but
doesn't map blockType == .intensification to BlockPhase.intensification.

Fix would be:
  var blockPhase: BlockPhase {
      if blockType == .deload { return .deload }
      if blockWeek == 1 && totalBlocksCompleted > 0 { return .postDeloadReintro }
      if blockType == .intensification { return .intensification }
      let midpoint = max(1, blockLength / 2)
      return blockWeek <= midpoint ? .earlyAccumulation : .lateAccumulation
  }

SEVERITY: Medium. Intensification blocks behave like accumulation blocks
for progression decisions and stimulus evaluation. The RPE table in
generateBlock correctly applies intensification RPE values (using
blockType, not blockPhase), so the workout structure is correct. But
the progression engine is less aggressive during intensification than
intended.

───────────────────────────────────────────────────────────────────────
9.4  Recomp infinite deload loop
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED BUG.

BlockType.next() case (.recomp, _) matches ANY current blockType for
recomp goal, including .deload. This creates:
  accumulation → deload → deload → deload → ...

After the first accumulation block, every subsequent block is a deload.
The user perpetually deloads.

Severity: HIGH. Recomp users are essentially locked into deload mode
after the first block.

Fix: Add explicit case before the wildcard:
  case (.recomp, .deload): return .accumulation
  case (.recomp, _):       return .deload

───────────────────────────────────────────────────────────────────────
9.5  Hypertrophy .reaccumulation never triggers
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

As traced in Section 6.1, deload exits for hypertrophy occur at
totalBlocksCompleted = 1, 3, 5, 7, ... (all odd). The condition
blockNumber % 2 == 0 is NEVER true at deload exit.

Result: hypertrophy training alternates accumulation ↔ deload forever.
The .reaccumulation phase (blockMultiplier = 1.15, higher volume) never
activates.

Severity: Low-Medium. Users still get effective training via accumulation
blocks. Reaccumulation would add variety and volume escalation across
mesocycles. Its absence makes the periodization less sophisticated but
not broken.

Fix: Adjust the modulo check. For example:
  case (.hypertrophy, .deload):
      return (blockNumber / 2) % 2 == 1 ? .reaccumulation : .accumulation
  This would count only non-deload blocks for the alternation.

───────────────────────────────────────────────────────────────────────
9.6  Powerbuilding .reaccumulation never triggers
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

As traced in Section 6.3, deload exits for powerbuilding occur at
totalBlocksCompleted = 1, 4, 7, 10, ... (all ≡ 1 mod 3). The condition
blockNumber % 3 == 1 is ALWAYS true, so intensification always wins.
The fallback case for .reaccumulation never fires.

Pattern: accumulation → deload → intensification → accumulation →
         deload → intensification → ...

Severity: Low-Medium. Same as hypertrophy — functional but less varied.

Also: intensification → accumulation transition has no explicit deload
block between them (falls to default → .accumulation). The built-in
deload week at the end of each block provides some recovery, but it's
a single week, not a full deload block.

9.7  Strength second cycle skips intensification
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

The condition `blockNumber < 3` only allows intensification in the
first cycle. After totalBlocksCompleted ≥ 3, all deload exits go
directly to peak.

Second cycle pattern: accumulation → deload → peak → accumulation → ...
(3-block cycle, skipping intensification)

Severity: Low. This may be intentional for advanced strength programming
where the athlete has established their work capacity and can peak more

───────────────────────────────────────────────────────────────────────
9.9  T1 continuity bonus off-by-one
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

In selectExercisesForMuscle(), the continuity bonus (+50 points) only
fires when blockNumber > 1. This means:
  blockNumber 0 → no bonus (first block — correct)
  blockNumber 1 → no bonus (second block — likely incorrect)
  blockNumber 2 → bonus fires (third block)

The user's T1 anchor from block 1 has no continuity preference in
block 2. This could cause the T1 exercise to change unnecessarily.

Severity: Low. The user can always swap back. And for block 2 the
stretch position score (+15) may still favor the same exercise.

Fix: Change to blockNumber >= 1 or blockNumber > 0.

───────────────────────────────────────────────────────────────────────
9.10  MRV signal scores may never decay
───────────────────────────────────────────────────────────────────────
Status: PROBABLE GAP (requires runtime verification).

MRVSignalEngine.computeScore() reads lastSignalDate from
ProgressionState. The decay formula: score = max(0, score - weeks).

However, lastSignalDate on ProgressionState does not appear to be SET
anywhere after signals fire. In finalizeWorkout(), only
inst.mrvSignalScores[muscle] is written (the computed score integer).
If lastSignalDate is never updated, it remains nil, and the decay
if-let check fails — meaning scores NEVER decay.

Impact: MRV signal scores would only grow (or stay at deload-reset 0).
Once a muscle accumulates signal points, they would persist until a
deload week resets the score to 0.

This could cause premature deload recommendations for muscles that
had transient fatigue signals.

Severity: Medium. The deload week reset (returning 0) provides a hard
reset, but between deloads, scores accumulate without natural decay.

9.13  Non-deterministic T2 selection
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED MINOR ISSUE.

ExerciseDictionary.all is a [String: ExerciseDefinition] dictionary.
Dictionary.values iteration order is not guaranteed. When multiple T2
candidates have the same score (same stretch position), the selection
order depends on dictionary iteration — which may vary across app runs
or Swift versions.

Impact: The user could see different T2 exercises prescribed for the
same inputs on different runs. This makes testing harder and could
confuse users who re-generate programs.

Severity: Low. Exercise quality is equivalent when scores are tied.

Fix: Sort by exerciseKey as tiebreaker to ensure deterministic selection.

9.14  Session set cap (G6) enforcement is log-only
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED MINOR ISSUE.

G6 validateSessionSetCount returns Bool and logs if count > 24, but the

The actual cap is enforced inline via:
  cappedSets = min(setsThisSession, maxSessionSets - sessionTotalSets)

So G6 is a redundant validation that only fires AFTER the inline cap
has already prevented exceeding 24. G6 as written can never trigger
(sessionTotalSets can never exceed 24 due to inline cap).

Severity: Negligible. The inline cap works correctly.

───────────────────────────────────────────────────────────────────────
9.15  selectExercisesForMuscle can assign fewer sets than requested
───────────────────────────────────────────────────────────────────────
Status: CONFIRMED.

Maximum assignable: T1(5) + T2a(4) + T2b(3) + T3(3) = 15 sets.
If setsNeeded > 15, excess sets are silently dropped.

Also, if T3 candidates are empty for a muscle (theoretically possible

In practice, this is bounded by the per-session cap (24 sets shared
across all muscles) and per-muscle MRV, so setsNeeded rarely exceeds
15 for a single muscle in a single session.

Severity: Low. Theoretical edge case.
